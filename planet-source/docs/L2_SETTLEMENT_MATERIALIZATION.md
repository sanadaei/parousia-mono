# 集落候補と局地L2地形の接続診断

2026-10-13。対象環境は **PC**。L0人口正本とL1配分から渡された候補一件を、保存された詳細地形上の住宅一区画・農地区画一ページ・地域端へのアクセス調査へ接続する診断例。

## 景観としての採用は保留

画面の直交した住宅配置・同型の12m住宅・矩形農地は、人口と面積の収支、地形上の保留、保存再利用を検査する仮配置。住宅の形状だけでなく、街路・宅地・農地の配置そのものが未採用であり、そのまま全球ランタイムへ接続しない。

この処理は `economicContext.layoutPolicy` を与えておらず、`createSettlementLayout` の旧 `population-districts@1` 経路を使っていた。以前の近景計画で課題とした反復格子・四角い農地リングへ戻ったもので、地形に沿う集落を実現した進捗とは扱わない。診断コマンドを `l2:diagnose-layout` へ変更し、この仮配置の生成・保存関数を共通core APIから外した。専用スクリプトと試験は明示的に診断モジュールを参照する。

次は [近景計画](../LOCAL_LANDSCAPE_PLAN.md)と[実地形との比較](EARTH_LANDSCAPE_COMPARISON.md)に沿う配置設計。地形と進入路、水へのアクセス、公共用地・生産用地から街路と区画を組み、住宅と農地を配する。既存のterrain-led経路も未完成なので、フラグの切替や家の装飾だけで受け入れとしない。複数地域を同じ広さ・縮尺で比較し、地形・集落・農地・道が一体として読めることを確認してから統合する。

## 正本と生成範囲

`makeL2SettlementDetail` / `createL2SettlementSurface` は、明示的に渡された `shape-first-candidate@1` のネイティブ格子と設計河床を、世界ID・親L1・handoff・球半径・配置・出典と一緒に識別する。最大32,768節点、格子間隔は各100m以下。詳細域外は高さ・水域とも未確認であり、粗いL1へ戻して建設可能と扱わない。

`materializeL2SettlementCandidate(surface,population,handoff,options)` は固定slotから候補を取り出す。候補のID・人数・原点を変更せず、詳細面で立地を再調査する。立地保留なら住宅・農地・道路を生成しない。

既存の住宅区画生成を使い、一区画は最大96戸、住宅一戸の人数仮定は5人。`housing.totalPopulation = requestedPopulation + unvisitedPopulation`、`requestedPopulation = representedPopulation + unresolvedPopulation`。公共建物を住宅数に数えない。別区画の参照は `districtIndex` で行い、全区画を一度に生成しない。

村の農地は **候補一件の整数需要** を200×200mの固定区画slotへ配り、末尾区画の幅を縮めて実面積を一致させる。全住宅区画の外側に置き、指定ページのみ標本調査する。未知・水域・勾配・住宅・道路幅との重なりは理由付き保留。`fields.totalDemandM2 = requestedM2 + outsidePageM2`、`requestedM2 = surveyedM2 + unresolvedM2`。町・都市の後背地供給は未解決として需要を保持し、ローカル畑を作ったことにしない。

地域端の入力済み調査点がある場合だけ、既存の局地道路探索を使う。橋は作らず、5kmまでの探索と道路幅の水域・敷地照合を行う。通過した道路を先に農地の阻害領域へ入れる。地域端までの道ができても、隣接地域の道路との接続は `receivingConnection: unresolved`。

候補・区画・農地ページ・調査点の識別で `CommittedMaterializer` に確定保存する。詳細面と入力条件を保存条件に含め、同じ保存へ異なる地形を上書きしない。一レコードの上限は4MiB。再読込では初回の形状と保留を使う。

## 再現と検査

```powershell
# 前段のL0/L1・候補資料がない場合
npm run l2:baseline
# 保存されたL1から固定三候補の接続を診断（景観として未採用）
npm run l2:diagnose-layout
```

入力は `reports/l2-settlement-baseline`、出力は `reports/l2-settlement-materialization`。CLIの二つの位置引数で入力・出力ディレクトリーを指定できる。既定の三候補のslotを固定しており、成功例を探すためにseedや原点を選び直さない。

今回の地域地形例には既存のseed生成器を用い、161×129節点、約8.85×9.77km、55.30×76.35mのネイティブ形状を追加した。L1の一点の標高を配置時の基準として平行移動し、局地の形を保つ。設計河床と仮の400mm/年流出注釈を使い、外部流入・洪水・飲料水を成立済みとはしない。住宅の敷地判定はこの格子の補間と設計河床上で行う。格子未満の小地形・土壌・基礎耐力は未生成・未検証。

ここで「ネイティブ」は入力の高さ格子を意味し、自然な詳細地形として受け入れたという意味ではない。候補ごとに独立した地形例を作り、親L1の一点の標高に合わせただけで、周辺の地形・排水・土地利用の連続性は成立させていない。細かい表示補間や敷地の標本間隔は、新しい地形情報の生成を意味しない。

固定三候補では、都市74,465人と村260人は詳細面の傾斜で保留。起伏地域の村284人では住宅27戸・135人分を配置し、149人を保留した。公共建物一棟は住宅数に含めない。この村の必要農地4,431,714m²のうち、今回のページ640,000m²で600,000m²が標本条件を通過、40,000m²が水域で保留、3,791,714m²がページ対象外。地域端への道は幅の水域・未知値確認で保留。

`review.html` は保存結果の独立したPC向け検査画面。詳細地形と配置輪郭を見比べ、通過・保留・今回の対象外を区別する。表示格子も住宅・農地・道路と同じ詳細サンプラから作る。土壌・食料確保・権利・農道の完成を、この画面の農地輪郭で証明しない。

## 現在のロードマップ

**L0統計 → L1配分 → L2候補受け渡し**が土台。局地詳細化・条件調査・保存は接続診断までで、詳細地形と村のリアリティは未受入。

次は地形の比較・必要な細部の設計と、地形・進入路・土地利用から決める村の配置。この受け入れを経てから、立地保留の扱い、農地への実アクセス、隣接するネイティブ地形と道路の接続、全球ランタイムへの採用へ進む。独立した三地域の地形例を、共有境界まで成立した全球地形と扱わない。長時間運用とPCのGPU描画・性能の受け入れも残る。

今回の実測・自動試験・PCブラウザー操作・参考レビュー・未実行事項は `reports/l2-settlement-materialization/verification.json` に記録する。元配布ZIPのSOURCE-MANIFESTは現在の変更コードの証拠として更新しない。

訂正前の接続診断チェックポイントでは全1,432試験PASS / 0 fail / 0 skip、buildはcore 160・完全一致alias 30・globe構文74が成功。そのチェックポイントの最後の表記補正ではHTML内のJavaScript構文とPC実ブラウザーを再確認した。三候補切替、地図と一覧の連動、保留の絞り込み、キーボード・ホイール・ドラッグを確認し、コンソールエラー0・横overflow無し。Geminiは画像閲覧ツールで三枚を参照し、住宅容量・保留住宅需要・隣接未接続の表記を参考レビューした。人口需要まで住宅容量とする案は採用していない。これらは村や地形の自然さの受け入れを証明しない。

今回の位置づけの訂正は `reports/l2-settlement-materialization/realism-scope-correction.json` に別途記録する。以前の検証・画像・コード差分は当時の診断チェックポイントとして保持し、今回のコードや景観の受け入れの証拠へ読み替えない。

全球ランタイムへの採用、PCのGPU globe、長時間運用、人間による景観・操作の受け入れは未実行・未完了。今回の実画面はCanvas2Dによる局地の保存結果検査。

敷地の四隅だけでは狭い河川を見落とす例があったため、建物内部と内部道路の幅も2m間隔で標本調査する。該当する建物・padを保留へ戻し、住宅人数と保存状態を更新する。修正前の未受入資料はQA履歴に隔離した。具体化generatorは@2へ更新したため、@1の具体化レコードは再生成が必要。L0/L1とネイティブ地形の版・候補原点は変更していない。
