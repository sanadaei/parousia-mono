# まず「それらしく動く」現在の最善版を作る

更新: 2026-10-13。目標は、これまでの有効な部品を組み合わせ、地形と川が読める景観を実際に動かせる形で渡すこと。形を先に比較して選び、階層・流量・生成理由はその後で整える。全球の物理・生態・都市を一度に完成させる計画ではない。

**対象環境**: PC。マウス・キーボード操作、PCブラウザーでの表示、PCのCPU/GPU・メモリを基準に設計・検証する。

## 1. 現在の基準版: 動かして確かめられるところまで接続済み

- **形**: 同梱 A（river-first）と、seed から川の枝・谷・丘陵を一緒に作る生成器。実地形と A/B/C を同じ約 8.85 × 9.77 km、共通の表示条件で比較できる。
- **階層・隣接**: 一枚の詳細形状から5段階を導出し、同じ元配列から隣接タイルを切り出す。別々に作った地形を境界だけで無理に合わせない。
- **通常画面**: 球面の通常ランタイムへ地盤・設計河床・水面を接続。宇宙から地域へ戻り、平面検査画面と切り替えられる。青い川記号を消しても水面を確認できる。
- **外への接続**: 条件が合えば、保存惑星に実在する受け側河川まで設計河道をつなぐ。適合する相手がなければ未接続と明示する。
- **保存**: 初回の数値形状、seed、出典、配置、河道版、流出口の識別を保持し、再読込・書出し・取込みで再利用する。既存の採用世界は自動で置き換えない。

2026-10-13 06:21 UTC の基盤チェックポイントは **1,348 tests PASS / 0 fail、build 成功**。クラウドブラウザで平面検査と球面 CPU 診断表示、保存復元を確認した。これは下記の見た目仕上げ前の記録で、見た目や GPU 性能の完成証明ではない。

根拠: [操作・契約](SHAPE_FIRST_REGION.md)、[検証記録](../reports/shape-first-end-to-end-qa/status.json)、[受け川への接続](../reports/shape-first-outlet-connection.md)。

### 「今までのベスト」の採用範囲

今回の組合せは **A/seed 生成の形 + 共通の詳細段階・隣接窓 + 通常球面表示 + 明示的な設計河道 + 実受け川 + 版付き保存**。

- B（侵食型）と C（広い谷・非対称斜面）は比較用の別案。A と混合済みとは扱わず、良い要素だけを次の小さな比較で試す。
- 実地形は自然さの参照。生成地形の高さへコピーしていない。比較図の実地形上の青線も DEM から計算した排水経路で、実測河川線ではない。
- 旧来の水収支・境界継承試作には再利用可能な保存・共有領域の仕組みがある。ただし、固定端点の矛盾や人工的な流域境界が残る方式を、そのまま今回の形の制約にはしない。
- 既存の森林・農地・集落・道路の実装は別の保存世界にある。今回の球面ドラフトでは旧配置を省略しており、それらを新地形へ統合済みとはしない。

## 2. 今回仕上げた範囲: 景観として読める基準版

**仕上げ後の検証**: 2026-10-13、最終コードで **1,356 tests PASS / 0 fail、build 成功**（core 154、互換export 30、globe構文74）。同梱Aとseed生成の全景、実水面の近景、操作パネルの開閉をクラウドのCPU診断表示で確認した。水深・配置・河道版・受け川の同一性も維持している。PCのGPU描画、全球ロードマップの完了を意味しない。

**今回採用した表示**: 地域内の相対標高と計測済みの斜面に応じた落ち着いた地表色、水面と任意の川筋ガイドを区別する配色、実寸1倍・傾き45度・正午を基準とした全景。朝の光・55度の視点も実画面で試したが、粗いメッシュの三角形が目立ったため初期表示には採用しなかった。長い技術説明は折りたたみ、操作パネルを閉じて景観を見渡せる。色や表示だけの変更で、元の標高・水深・保存形状は変えていない。[比較と採否](../reports/visual-finish/design-notes.md)。

**成果物**: 通常の起動手順で開き、同梱 A と seed 生成を試し、拡大・縮小しても谷・斜面・川・岸を読み取れる作業版。説明図だけで済ませず、実画面と再現手順を添える。

1. 一様な緑の地面・青い水に見える部分を改善する。現在の形と水面を使い、陰影、地表色の変化、岸と谷底の区別を整える。
2. 同じ形・同じ視点の仕上げ前後を比較する。形状の弱点を色だけで解消したことにせず、必要な地形改善は次項へ分ける。
3. 地域全景、斜めの近景、支流の合流、流出口から受け川の接続を確認する。川記号の有無を切り替え、記号が水面の欠落を隠していないことを見る。
4. 最終コードで全試験と build、seed 切替、画面往復、保存復元を再確認し、実際に確認した描画経路を記録する。

**この一版の完了条件**:

- 地形の起伏・谷筋・水際が複数の縮尺で判別でき、従来の一様な色より改善が確認できる。
- 表示の改善で標高・水深・河道接続・保存済みの同一性を壊していない。
- 起動・操作・保存復元が再現でき、未接続や保存不能などの状態を隠さない。
- 最終検証と残る見た目の弱点を添えて渡せる。全面的な物理改修や無期限の磨き込みを納品条件にしない。

### 2026-10-13: 人の景観に向けたL0分布とL1受け渡し

ユーザーの追加指示により、全球の人口・村・町・都市を統計分布として持つ土台を追加した。既存の農業人口計画を正本とし、L0は地域の7整数予算、L1は実面積と相対適性による子への配分を保存する。適地がない親の予算は未配分に残し、親=子+未配分を全7項目で検査する。場所・家・農地・道はまだ具体化しない。

`npm run l0:baseline` でL0/L1の実データと独立した全球確認画面を作る。既定例は人口1億、村300,864、町3,052、都市40をL0の1,754人口区画に持つ。L1 256×128では99,898,832人を配分し、101,168人・村310・町3は親の未配分として保持する。画面は密度の共通尺度、親子予算、未配分への移動、キーボード選択を持つ。これは現在開いている旧保存世界の集落を増やした表示ではない。

通常の気候付き惑星生成・世界保存にもL0分布を接続し、人口正本と一致しない分布を拒否する。L1の識別と保存条件に親分布IDを含め、通常の世界セーブのキー整列後も分布IDが一致する。現行の24MiB保存枠を維持する。今回の変更は旧配布ZIPのSOURCE-MANIFESTと一致しない開発差分であり、旧ZIPの検証記録を新コードの証拠として更新しない。

**前段の完了範囲**: L0の統計分布・保存・L1配分・確認画面まで。上の集落数は前段の仮定と検証例。根拠は[仕様](L0_REVIEW.md)と`reports/l0-settlement-baseline`の検証資料。

### 2026-10-13: 集落規模と地域のL2候補

人口正本を`agriculture-population@2`へ進め、規模仮定を保存した。既定では町1,000人以上、都市25,000人以上。極小の町になる人数は村側へ戻し、L0→L1では集落個数に人数を結び付ける。総人口・容量を変えず、村町都市の内訳を更新した。個別候補はゼロ和の仮ばらつきモデルを使い、人数・ID・原点はページと参照順で変わらない。

`npm run l2:baseline`は全球分布と3代表地域の限定候補ページを保存する。既定のL0人口1億、村301,475、町2,724、都市40。L1へ99,898,832人を配分し、101,168人を親の未配分として保持する。農地は必要面積の見積もり。保存L1高さ・水域マスクによる広域選別を通しても、L2の敷地成立を確定したことにはしない。保存ページの再読込では初回の選別を使い、7整数予算と耕地需要を保持する。

**前段の完了範囲**: L0統計・L1配分から、規模付きの地域候補・農地需要・L2受け渡しまで。次はL2の詳細地形上での立地・敷地、実際の農地と生活圏、隣接地域への交通候補・接続道路。通常の参照時集落生成にも新規模仮定を適用したが、新しいL1候補を全球ランタイムで実敷地へ採用する統合は残る。下記の地形改善と両立させる。[契約](L2_SETTLEMENT_HANDOFF.md)と`reports/l2-settlement-baseline`の新検証資料を参照。

### 2026-10-13: 固定候補と局地地形の接続診断（景観として未採用）

保存済みの固定三候補に、既存のseed生成器によるネイティブ詳細地形と同じ設計河床サンプラを接続した。住宅一区画・農地一ページ・地域端への道路を条件調査し、人口・需要面積・保留を確定保存する。二候補は傾斜で保留、起伏地域の村では住宅27戸・135人分と農地60万m²の輪郭を得たが、149人・農地4万m²・地域端への道路は保留。ページ対象外の需要も残す。

**現在位置**: L0統計・L1配分・L2候補受け渡しが土台。局地地形へつなぐ予算・条件調査・保存は診断例までで、詳細地形と村のリアリティは未受入。今回の処理は既存の `terrain-led-neighborhood@2` を通さず、旧来の直交配置と矩形農地を使っていた。そのまま本線へ採用しない。[診断の範囲](L2_SETTLEMENT_MATERIALIZATION.md)。

**統合前の順序**: 下記の地形比較と、[近景計画](../LOCAL_LANDSCAPE_PLAN.md)の街路・土地利用方針へ戻る。谷底・斜面・川岸・段丘・支谷を同じ縮尺で比較し、地形と進入路、水へのアクセス、公共・生産用地から街路、宅地、住宅、周辺農地を決める。形を自然にするための一様なランダムずらしは採用しない。既存のterrain-led経路自体も完成景観として受入済みではないため、接続しただけで完了とはしない。複数の地形条件を地域・村・街路の縮尺で確認してから、隣接地形・道路と全球参照へ統合する。PC前提を維持する。

## 3. 次の限定改善: 形の豊かさと必要な細部

優先順は次の通り。毎回「同じ広さ・同じ縮尺の実例 → 小さい変更 → 比較 → 採用または保留」で進める。

1. **谷と川の変化**: C の広い谷・非対称斜面、B の侵食的な尾根や細い谷を候補として試す。支流の密度、合流角、長い直線、似た断面の繰り返しを見比べる。大量のノイズ追加や、一案だけの磨き込みを避ける。
2. **近景で必要な情報**: 岸、段丘、支谷など、現在の元格子では表現できない形を特定してから詳細ソースを追加する。表示だけを細かくして新しい地形ができたとは扱わない。
3. **複数地域へ拡張**: 必要な広さを持つ共通形状を先に作り、隣接領域へ切る。既存の一枚を二分しても世界の面積は増えない。混在する表示段階の辺・水路・保存境界も確認する。
4. **表示負荷**: 近景の過剰な細分化、読み込み待ち、岸の小さな描画乱れを実測して直す。PCのGPU実機と構成による性能差は別途確認する。

### 粒度を混同しない

- **元格子（native grid）**: 現在の基準形状は 161 × 129 点、東西約 55.30 m・南北約 76.35 m 間隔。この高さ配列を細かく補間しても、その間隔未満の地形情報は増えない。
- **解析的な河道（subgrid）**: 川筋と設計断面から、元格子より細い河床・岸・水面を座標ごとに計算する追加モデル。狭い川を扱えるが、地域全体が同じ細かさで生成済みという意味ではない。幅・深さは現在の仮の設計規則で、水理較正ではない。
- **詳細段階1〜5**: 同じ元形状を粗く見せる表示・検査用の段階。11 × 9 → 21 × 17 → 41 × 33 → 81 × 65 → 161 × 129 点。隣の段階との格子間隔は2倍違い、最終段階より細かい地形は含まない。
- **L0/L1/L2**: L0 は大陸・海・広い起伏と気候の大づかみ、L1 は広域地形・排水の具体化、L2 は地域の詳細化という責任分担。固定の km 数や上の5段階の別名ではない。今回の地域ドラフトを作れたことだけで、全球の L0 → L1 → L2 が完成したとはしない。

**細かくする判断**: まず今の元形状のまま表示を仕上げる。次に比較画像で不足が見えた範囲へ、新しい版の詳細ソースを追加する。隣接2倍の細分化を比較の出発点とし、段階数そのものを品質目標にはしない。親の粗い川位置は必要に応じて幅のある候補域として扱い、細部の選定前から不適切な固定端点にしない。採用済みの形や接続条件を変える場合は明示的な新しい版にする。

根拠: [世界階層の役割](WORLD_LAYER_ROLES.md)、[段階的詳細化の比較](PROGRESSIVE_LAYER_REFINEMENT.md)、[未採用の次段階と端点矛盾](NEXT_LOCAL_LAYER.md)。

## 4. その後に進める統合

- **水文**: 仮流量から、上流供給・地域流出・受け川への増分を一度ずつ計上する水収支へ。湖・貯留・季節変動・水位応答などは個別に検証する。現在の水面の幾何的連続性を、全球水収支や洪水計算の完成と言い換えない。
- **環境**: 地形・気候・水辺に沿った森林、開けた土地、湿地を接続し、広域色と近景の樹木・地面の整合を取る。装飾色と成立が確認された生態条件を区別する。
- **人の景観**: 新しい地形に適合する農地、村・都市、道・渡河を接続する。旧配置をそのまま重ねず、土地利用の連続性と実際のアクセスを確認する。
- **全球運用**: 保存互換、広域の接続、読み込み時間、長時間メモリ、異なるPC構成での描画を確認し、地域の成功を全球へ広げる。

既存の長期目標・残件は [ROADMAP](../ROADMAP.md)、[近景計画](../LOCAL_LANDSCAPE_PLAN.md)、[環境統合](ENVIRONMENT_INTEGRATION.md) を参照。この文書はその全完了宣言ではなく、まず渡す一版と、その後の優先順位を定める。
