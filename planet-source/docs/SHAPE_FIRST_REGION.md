# 形を先に作り、階層は後から導く

今回の試作は、もっともらしい地形と水系の形をまず比較し、その形を選んだ後で理由・流量・境界接続を詰める。古い親地形、固定アンカー、流出口、水収支を先に正解として固定しない。現在は既存の惑星ビューから明示的な球面ドラフトを選べる。採用済みの世界データは書き換えず、詳細形状を通常の地形照会・地表メッシュ・カメラへ接続する。全球の水文シミュレーションが完成したという意味ではない。

## 比較と初期案

- A / river-first：枝分かれのつながりが読み取りやすく、今回の階層の初期形状。40本の設計川筋と谷を一緒に作る。
- B / eroded：丘陵を削り、得られた排水経路から川筋を抽出する別案。侵食は形状探索のヒューリスティックで、物理較正ではない。
- C / valley：広い谷底と非対称の斜面を組み立てる別案。後でAと組み合わせる候補だが、現時点で混合したとは扱わない。

比較図：`scripts/experiments/shape-first/comparison/shape-first-four-way.png`。同じ約8.85×9.77 km、161×129点、各範囲最低地点からの相対標高の共通色尺度、陰影の高さ強調2倍。実地形側の青線はDEMから推定したD8排水経路で、実測河川ではない。表示条件JSONと再描画スクリプトも同じ場所にある。実地形は比較専用で、A/B/Cの高さ生成には使わない。

## 入出力契約

入力：`schema: shape-first-candidate@1`、`grid`（columns, rows, cellSizeM, cellSizeYM, row0=north, yDirection=south）、行優先の有限な標高配列 `elevation`、`rivers: [[{xM,yM},...],...]`。水平・標高ともm。座標原点は北西、Xは東、Yは南。任意のseed/notesは保持する。新しい候補にも同じ契約を使える。

詳細形状161×129から16,8,4,2,1間隔で厳密に節点を抜き出し、11×9→21×17→41×33→81×65→161×129を作る。隣接レベル間の区間数は必ず2倍。同じ詳細形状から作った粗い表示であり、古い粗地形へ詳細を押し込めない。ネイティブ未満の解像度を生成したり、粗い形から細部を再生成したりしない。`--levels N` は整数2倍間隔で割り切れる範囲のみ。

元JSONのUTF-8 SHA-256、生成器を指定した場合はそのSHA-256、ネイティブ格子と派生手順を保存する。ハッシュは入力の識別であり、任意の生成器による再現を自動証明するものではない。河川は共通のm座標と各レベル上の分数格子座標で保持し、粗いレベルでも勝手に引き直さない。3桁丸めによる境界外1 mm以内の端点のみ境界に寄せ、数と最大移動距離を記録。それを超える境界外座標は拒否する。

各レベルのRMS/最大誤差は、そのレベルを双線形補間してネイティブ形状と比較した「形の保持度」の説明値。採用閾値ではなく、流量・排水・侵食の検証でもない。粗い点抜きは狭い谷を見失うことがあり、比較画面で確認する。流量は形状選定後に説明を付ける。現在の注釈は一様な仮の正味流出量400 mm/年による年平均の算術であり、地形に基づく流域検証ではない。

## 隣接領域は共通の形から切り出す

`src/core/shape-first-regions.mjs` の `createShapeFirstRegions(candidate, options)` はブラウザでも使える純粋な関数。まず設計済みの一枚の形を受け取り、その後で整数格子窓に分割する。領域別に独立生成した境界を後から無理に混ぜる処理ではない。

```sh
node scripts/experiments/shape-first/build-adjacent-regions.mjs
node --test test/shape-first-regions.test.mjs
# reports/shape-first-neighbors/preview.html を開く
```

保存済みAの161×129点、約8.85×9.77 kmを、東西2枚の81×129点、各約4.42×9.77 kmに切り出す。元の55.30×76.35 m間隔を保ち、ネイティブ格子より細かい情報は作らない。この例は世界を2倍の面積に拡大したものではない。新しく大きな領域を作る場合は、その全域の形を先に生成してから同じ関数で分割する。

各タイルは6×9→11×17→21×33→41×65→81×129点の5段階。隣接段階の区間数は2倍、共有辺の129点は同じ元配列の節点なので標高差は厳密に0。粗い段階も同じ節点を使う。混在LODを描画する側は共有辺を同じ解像度で扱うか辺分割を揃える必要があり、この配列契約だけで異なるLOD間のメッシュ隙間まで解消したとは扱わない。

河川は共通の全域m座標で格子窓にクリップし、元の河川ID・区間番号・区間内パラメータを保持する。出入りが複数回ある河川は複数の断片になる。境界ポートは同一の交点、河川ID、元区間、仮流量を両側で共有する。単なる接触や境界に沿う川は領域間流入と数えない。地形と川筋を流量のために移動しない。

`waterAnnotation` と対応する `riverIds` を渡した場合、既存の仮流量を共有元区間からそのまま参照する。`pointOrder: 'downstream_to_upstream'` を明記したAでは、両側のポートの流入・流出方向が対応する。水源を追加せず、元全域の水収支だけを利用する。これはタイルごとの集水域検証ではなく、既存の合流を区間単位に量子化した仮注釈の受け渡しである。注釈を渡さない場合の流量は0ではなくnull（未定）。

出力は `shape-first-adjacent-regions@1`。`domain` に元形状、`tiles` に各格子窓・各レベル・クリップ河川・ポート、`seams` に共有点と接続ポートが入る。時刻・乱数を持たず、同じ入力で同じ出力となる。例のビルダーは元JSONのSHA-256を保存し、保存後に読み直した完全一致を検証する。プレビューは全域共通の陰影計算を使い、継ぎ目表示を消して形状の連続性を確認できる。

2×2以上の分割で川が四隅の交点を斜めに通る場合は、`cornerTransfers` に実際に川の長さが存在する2タイル間の接続を一度だけ保存する。点で触れるだけの中間タイルに流入・流出を複製しない。仮流量を渡す場合は標高・川筋のSHA-256、河川IDの順序、格子数・実面積が元注釈と一致することを検証し、別形状の流量の誤用を拒否する。


## 既存アプリで開く

```sh
npm start -- --no-open
# 通常の惑星画面で「地形ビュー」→「形を先に作る惑星地形（試作）」
# または /src/globe/index.html?terrain=shape-first
```

- `terrain=shape-first` は通常の球面ランタイムを使う。標高照会、LODメッシュ、カメラの地表参照が同じ詳細形状を参照する。地域の外側だけを保存惑星へなめらかにつなぎ、内部の詳細を古い粗地形に押し込めない。保存世界には別のドラフトIDを割り当て、旧集落・道路の配置はドラフト内で省略する。
- 初期表示は地域を見渡す高度。宇宙へ移動して戻れる。`sfView=global` は全球から開始し、「形状優先の地域へ」で選んだ地域へ移動する。
- `terrain=shape-first-inspect` は同じソースの平面検査ビュー。詳細段階1〜5（地域内の表示段階であり、世界のL0/L1/L2の役割名ではない）、自動段階、ホイールズーム、ドラッグ・矢印キー移動、川選択と区間の仮流量、継ぎ目・接続点を確認できる。隣接タイルには同じ段階を適用し、陰影は全域の勾配を使って境界の照明ずれを避ける。
- 両画面の地形ビュー切替は選択seedと惑星上の配置を保つ。検査ビューには「この形状を惑星で見る」もある。「保存した惑星へ戻る」は元の採用世界へ戻る操作。
- 既定は同梱形状A。「形状の入力」でseed生成を選び、seedを入力して「生成して表示」。生成は専用Workerで行い、検査画面で連続送信した場合は古い生成を中断し、最後の要求だけを表示する。形状生成の後で、共通の階層ビルダー・仮流量ビルダーを使う。CLIとブラウザで別の数式を持たない。

### 配置と保存

`sfLat` / `sfLon` は中心緯度・経度、`sfTransition` は地域外の接続帯幅（既定4000 m）、`sfElevation` は元の形を上下させる一様な標高オフセット。未指定のオフセットは保存惑星の地域中心との対応に加え、河道を含む地域の最低点が海面より30 m以上になる条件を満たすように決める。30 km以内に検証可能な保存河川の受け側がある場合は、流出口からその水面へ下れる設計勾配も満たすよう調整する。指定オフセットが接続先に対して低すぎれば、無理につなげずエラーにする。実際に使った値と `sfParentWorld`（親世界のID）はURLに確定され、再訪時に親世界が一致しない場合は拒否する。ドラフトIDは元形状・水注釈・親世界・配置・接続帯・標高オフセットに結び付く。

生成seedの最初の候補JSON・全段階・水注釈は、採用世界と分離したブラウザ保存領域に保持する。再訪時は保存した数値を照合して読み込み、更新後の生成器で勝手に作り直さない。現行UIの範囲・格子・出口の選択条件は固定なのでseedが保存キー。将来、範囲や出口・起伏倍率などをUIで変えられるようにする場合は、それらの条件も保存キーへ含める必要がある。

「生成した形状を保存・復元」からJSONを取り出せる。形式 `shape-first-runtime-draft@1` は生成seed、元形状のSHA-256、初回時刻、数値バンドルと `shape-first-view@1` の配置記録を持つ。配置には選択した同一サイト内の世界マニフェスト、親世界ID、緯度経度、上下オフセット、接続帯、選択ビューが入る。記録は16 MiB以下。取込みではデータと配置の形式を検査し、同じseedの別形状が既に保存されていれば上書きしない。別のブラウザで元の世界ファイルが利用可能なことも必要。記録自体に親惑星全体は含まれない。

ブラウザ保存が拒否された場合は一時表示であることを明示し、再訪前の書出しを促す。壊れた保存形状は黙って再生成せずエラーにする。読込時に元形状のハッシュ、各段階の節点、河川IDと向き、水注釈の出典、親子循環、供給量の算術的な整合を検査する。これは自然な侵食・集水域・水理を証明する検査ではない。

### 球面ビューの設計河道と検査ビューの青線

検査ビューの線幅は引き続き仮の供給量を表す画面上の記号。球面側の `src/core/shape-first-channels.mjs` は、その注釈から別途、設計幅 `clamp(3+8√Q,3,42)` m、設計深さ `clamp(0.3+0.55∛Q,0.3,3)` mを導く。形状を選んだ後の設計規則で、水理的な容量から求めた幅ではない。

親川から子川へ順に合流水位・幅・深さを共有し、子川の上流へ最大(50 m, 親幅の3倍)の距離で移行する。現在の河道契約は `shape-first-designed-channels@2`。根の川の水位を元の設計谷床より0.15 m低く置き、物理的な設計河床はそこから設計深さだけ下げる。子川の水位は親川の合流水位から元の設計谷床の上流方向の上昇を使って導く。元の `designBedElevationM` を掘削後の実際の河床と同一視しない。断面は解析的な放物線の湿潤部と滑らかな岸の接続帯。河道外では元の標高、河道内では明示的な設計により切下げ・盛上げの両方があり得る。元の候補配列そのものは変更しない。

球面の地盤・水面・水深は同じ河道評価器から得る。これは水理平衡、洪水、堆積・地下水、全球の水系接続を認定するものではなく、幾何的に近いだけの交差を新しい合流とは扱わない。


配置記録は `sfRuntimeVersion`（現在 `shape-first-sphere@2`）、`sfChannelVersion`（現在 `shape-first-designed-channels@2`）と `sfOutletIdentity` も保持する。流出口識別子は検証済み受け側・接続仕様・設計経路の全体をハッシュ化したもの（未接続は `unconnected`）。再訪時は同じ契約で接続を復元し、バージョンまたは接続の識別子が違えば表示を拒否する。受け側や経路を黙って別のものへ変えない。球面の配置が未確定の間は配置を含む書出しを拒否する。河川記号の表示 `sfSymbols` も保存できる。


流出口は30 km以内の保存河川から候補を選び、実際の地形照会で受け側の水面と水源IDを照合したうえで幾何的な接続経路を設計する。適合する受け側がなければ未接続と表示し、存在しない接続を補わない。これは流出口から保存河川までの地形・水面の接続であり、受け側の流量増分・水位応答・全球水収支まで解いたものではない。

ユーザーが意図的にA/別seedへ切り替える際は、前の形状に由来する流出口識別子と上下オフセットを外して新しい形状の配置を計算する。緯度経度・接続帯・親世界・モデルバージョンは保つ。同じseedの再読込および配置記録の復元では、元のオフセットと流出口識別子を維持して照合する。
