# 開発指示書：Google Earth型 連続全球〜局地体験と動的LODストリーミングの実現

文書番号: `INSTRUCTION-LOD-20261009-01`  
ステータス: `ACTIVE`  
対象: 設計・実装担当エンジニア / Worker エージェント

---

## 1. 背景と開発の意図 (Context & Motivation)

### 1.1 これまでの成果
本プロジェクト（`continuous-terrain-adapter`）は、離散的な格子データを出発点としながら、任意のメートル座標で標高・勾配・法線・水深を決定論的に取得できる「連続数値場アダプター」としての基礎を固めてきました。河道掘削、切盛土造成、建物敷地平坦化、通行性評価などの幾何合成ロジックも整備されています。

### 1.2 直面している根本的課題
しかし、**当初構想していた「Google Earth のように全球から局地までシームレスに繋がり、視点に応じて動的に詳細化されていく体験」には至っていません**。

現在の実態は以下の制約に縛られています：
- 全球データを保持していても、表示時には「中心座標を指定した最大半径100kmの正距方位図法による2D矩形」を静的に1枚切り出している。
- 全球全体を見渡すズームアウトは幾何学的に制限（`RangeError`）され、別の地域を見るには画面をリロード（再生成）する仕様になっている。
- 現在実装されている「LOD」は「サンプリング間隔を変えても同一座標で値が狂わないこと（サンプリング決定論）」の検証であり、視点に応じて段階的にデータを読み込む「動的ストリーミング（Paged LOD）」ではない。
- ビジュアライザは Canvas 2D による平面マップであり、3D地球儀として球体を俯瞰・周回する基盤がない。

この結果、「数学的には連続参照できるが、アプリケーションとしてはシームレスな地球儀を触る体験ができない」という大きなギャップが生じています。

## 2. 達成すべき目標 (What to Achieve & User Experience)

担当エンジニアには、以下の**ユーザー体験およびシステム機能の達成**を求めます。

### 達成目標 1: 全球〜局地のシームレスな連続遷移 (Seamless Continuous Navigation)
- 宇宙空間から地球全体（全球）を見渡すマクロ視点から、特定の国、地域、街、そして道路面や建物敷地（地表メートル単位）のミクロ視点まで、**画面のリロードやシーン切り替えを挟まず、滑らかにズームイン・ズームアウト・パン（周回移動）できること**。

### 達成目標 2: 段階的詳細度による動的ストリーミング (Paged LOD & Streaming)
- 地球全体の膨大なデータを一度にメモリへ読み込むことは不可能なため、**「いまカメラに見えている範囲」かつ「カメラ距離に応じた適切な解像度」の地形のみを動的・非同期に読み込み・生成・描画すること**。
- 遠景は粗い低解像度で描画し、カメラが近づくにつれて徐々に高精細な詳細地形、河道、造成地が現れること。
- 視界外へ外れた領域や不要になった過去のタイルは自動的に解放され、**有限のメモリ容量内で安定動作し続けること**。

### 達成目標 3: Core 数値場（アダプター）との論理的一致 (Fidelity to Core Samplers)
- 画面上で描画されている 3D 地形・水深・道路・造成地は、これまで構築してきた Core アダプター（`global-terrain`, `surface-water`, `road-earthwork`, `building-pad` 等）のサンプリング計算結果と論理的・視覚的に整合していること。
- 「画面で見えている形状」と「インスペクターや通行性エンジンが評価する値」が乖離しないこと。

## 3. 満たすべき制約条件と非機能要件 (Constraints & Quality Requirements)

どのような設計・実装方式を採用する場合でも、以下の品質ゲートをクリアしてください：

1. **フレームレートと応答性 (Responsiveness)**:
   - 連続的なカメラ移動やズーム操作中、メインスレッドが計算負荷でフリーズ（ブロッキング）しないこと。
   - 常時 **30fps 〜 60fps** を維持し、操作感が快適であること（重いサンプリング計算は非同期化・Worker化等を検討すること）。
2. **メモリ上限の厳守 (Out-of-core Stability)**:
   - 長時間ズームや移動を繰り返してもメモリリークせず、ブラウザのヒープメモリ上限（例: 512MB〜1GB程度）内に収まり続けること。
3. **視覚的破綻の抑制 (Visual Continuity)**:
   - 異なる解像度（LODレベル）が隣り合う境界において、地形メッシュに隙間（Cracks/裂け目）が開いたり、法線が断絶して不自然な影が出ないこと。
   - タイルの詳細度が切り替わる瞬間に、激しいポリゴンのチラつきや不快な飛び（Popping）を最小限に抑えること。
4. **保守性と依存性**:
   - 既存のコードベース（Node 22 ESM、外部依存ゼロ志向）の設計思想を尊重しつつ、3D描画やストリーミングに真に必要な技術を合理的かつ最小限に選定すること。

## 4. 担当エンジニアに設計・選定を委ねる事項 (Open Architectural Decisions)

**以下の具体的な設計・アーキテクチャ・アルゴリズム選定は、担当エンジニア自身がトレードオフを比較検討し、最善の解を導き出してください。特定の方式に縛られる必要はありません。**

1. **大域 3D 空間モデルおよび座標系の設計**:
   - 球面直交座標（ECEF: 地心直交座標系）を直接用いるか、局所投影の動的タイルツリーを用いるか、あるいは別の空間座標表現を採用するか。
   - カメラが地表数メートルに近づいた際の浮動小数点精度問題（Jitter / Z-fighting）をどう解決するか。
2. **球面空間分割・タイル階層構造の選定**:
   - Cubed-Sphere（立方体球面四分木）、経緯度QuadTree（TMS / Slippy Map型）、正二十面体分割（HEALPix / Icosahedron）、あるいは CDLOD（Continuous Distance-Dependent LOD）など、どの空間分割アルゴリズムを採用するか。
3. **描画基盤（3D Graphics Pipeline）の構成**:
   - WebGL 2.0 ネイティブ実装、WebGPU、あるいは軽量な 3D ライブラリ（Three.js 等）を活用するか。
   - 地形起伏の表現にディスプレイスメントマッピングを用いるか、動的メッシュ生成を用いるか。
4. **非同期ストリーミング・キャッシュ・アンロード機構**:
   - Web Worker や OffscreenCanvas をどう活用してバックグラウンドサンプリングを行うか。
   - LRU キャッシュ、優先度付き要求キュー（Priority Request Queue）の設計。
5. **LOD境界の継ぎ目（T-Junction / Crack）対策の技法**:
   - スカート幾何（Skirt Geometry）、頂点モーフ（Geomorphing）、ステッチング（Stitching）など、どの手法で境界の連続性を担保するか。

## 5. 期待する納品物と受入基準 (Deliverables & Acceptance Criteria)

### 期待する納品物
1. **アーキテクチャ設計提案書**:
   - 採用した空間分割方式、座標系、描画パイプライン、キャッシュ構造の選定理由とトレードオフの整理。
2. **プロトタイプ / 実装コード**:
   - 宇宙視点から地表視点までシームレスにズーム・移動できる動的ストリーミング地球儀。
3. **動作検証・ベンチマーク記録**:
   - フレームレート推移、メモリ使用量推移、LOD切り替え時の整合性確認結果。

### 受入基準
- [ ] 宇宙空間の全球全景から、地表の道路・造成・河川が視認できるスケールまで、シームレスかつリロードなしにズームイン・ズームアウトが可能である。
- [ ] カメラ視点に応じて必要な解像度のみが段階的に読み込まれ、視界外のタイルが適切に破棄されてメモリが安定している。
- [ ] 操作中に画面がフリーズせず、快適な追従性（実用的なフレームレート）が保たれている。
- [ ] タイル境界に目立つ裂け目がなく、既存の Core 地形アダプターの数値場と整合している。
