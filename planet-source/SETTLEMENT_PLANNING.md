# 固定された集落配置と全球共通の日照

## 目的と今回の境界
見た目を磨く前に、施設の存在・立地・入口・土地利用を説明できるようにする。
村・小都市・交易拠点は異なる。全施設を全村へ置く方式にはしない。
最初の史的参考範囲は中世ヨーロッパ（特に英国の集落資料）。他地域・宗教・時代へ普遍化しない。
第一次～第三次産業は整理用の現代的分類であり、中世人の制度そのものではない。

## 配置の正本
世界の生成・明示的編集時にだけ配置を決定する。決定済みの区画ID、施設ID、座標、敷地、向き、供給元と選定理由を保存する。
カメラ・LOD・現在時刻・表示順・再訪問・ブラウザ再起動を乱数や配置の入力にしない。
変更は新しい世界版として出力し、既存の保存世界を勝手に再生成しない。

## 日照
planet-fixed座標で一つの太陽方向を共有する。入力は一日の進み、太陽の赤緯、基準正午経度。
緯度経度により高度・方位・昼夜・地方時を導出する。村で『朝8時』を設定したら全球の時計を変更する。
村を移動しても、その場所を自動的に朝8時にしない。壁時計を読んで勝手に進めない。
設計時の日照（季節・時間帯の採光条件）と表示時の日照を区別する。夜になっても家の向きは変わらない。
現在のsolar-lightは天文学的公転のシミュレーション、地形遮蔽、建物の投影影、気象ではない。

## 施設群
- 生活基盤: 住居、井戸、泉の取水、倉庫、廃棄・堆肥場。
- 第一次: 穀物畑、菜園、果樹園、放牧、漁場、管理林、石切場、鉱山、粘土採掘、製塩。
- 第二次: 水車・風車・手挽き製粉、パン焼、醸造、屠畜、乳加工、燻製、木工、炭焼、製錬、鍛冶、陶工、紡績、織布、縮絨、染色、皮なめし、革細工、仕立。
- 第三次: 穀倉、倉庫、市、宿、酒場、厩、礼拝、墓地、領主館、集会、施療、教育、見張り、渡し。
家庭内作業と専業施設は将来的に同一敷地の複数用途として扱う。現段階の単一用途スロットではその細分化はしない。

## 硬い条件と選好
硬い条件: 敷地面積、斜度、洪水リスク、通路、資源・権利・技術の存在、原料供給距離、安全離隔。
選好: 道への距離、運搬距離、中心への近さ、採光。
水が見えることと飲めること、川があることと水車を回せる落差・流量があることは異なる。
汚染施設は安全な排出先、取水施設は保護された集水域を明示する必要がある。方角だけで『下流』と見なさない。
市場・領主館・教会・学校などの存在には人口だけでなく制度的条件を要求する。
原料がないなら配置しない。域外供給は所在と出所のある入力として登録する。

## 実装段階と残件（随時更新）
1. facility catalogue: 候補の用途、必要資源・制度、空間条件。
2. settlement planner: 調査済み区画を入力し、固定配置・供給リンク・配置できなかった理由を返す。
3. solar-light + viewer: 共通光方向と時刻操作。
4. settlement-survey / village-economy: 既存区画・明示した土地候補を地形に照合し、通路・住居確保を調べ、新しい保存版へ結合。
5. settlement-transport: 保存済み道路の交差点を使って供給距離を計算。未接続な道同士は無限大として拒否。

現段階のplanSettlementは生成用APIであり、既存の村が自動で48種類へ変わったという意味ではない。
静的供給リンクは生産計画。生産能力・労働人口・季節収穫量・在庫を充足した証明ではない。
汎用planSettlement単体は直線距離を既定とするが、village-economy接続では実道路グラフへ置き換える。路面の荷車適性、渋滞、運搬能力、季節通行止めは未モデル化。
施設の外観差、内装、装飾は今回の目的ではない。

## LOD・処理予算
上限512区画、128要求、128配置。カメラ移動中にはプランナーを呼ばない。
土地利用は区画情報として保存し、各作物・樹木・商品・住人を先に全生成しない。
既存BuildingLayerは近隣chartだけ読込み、同時2ページ、形状・再利用キャッシュを各1MiBに制限する。
資源条件を満たせないこととメモリ予算で表示を省略することを同じ『存在しない』にしない。


## 実際に試す
起動: `node scripts/start-planet.mjs`（既存起動方法がある場合はそちら）。
- 全球画面の「全球共通の日照」で現在地の時刻・季節の光方向を変更。
- 全球画面の「集落の配置理由を見る」は、その表示元と同じ保存世界を読む。旧世界に計画がなければ未計画と明記する。
- 保存済み実例: `/src/globe/settlement.html?recipe=/examples/settlement-planning/actual-village-recipe.json`
- 入力: `examples/settlement-planning/village-profile.json`
- 実出力: `actual-village-result.json` と `actual-village-recipe.json`。例の土地適性・制度・羊毛輸入は仮定として記録してある。

新しい保存版を作るコマンド:
```
node --max-old-space-size=256 scripts/plan-village-economy.mjs examples/planet/generated examples/planet/planned settlement:2640 examples/settlement-planning/village-profile.json
```
作成後は `/src/globe/index.html?world=/examples/planet/planned/manifest.json` で開く。
入力の保存先と出力先を同じにすると拒否する。生成完了後のカメラ操作・再読込では再計画しない。

実例: 人口100人、仮定の1世帯5人。32棟中23棟を住居として残し、9棟の用途を割り当てる。
別途2区画を穀物畑と管理林として保存。土地用途は現状2D配置検査で表示し、3Dでは作物や樹木を大量生成しない。
11用途成立、5用途見送り。物理的に不適切な土地・通路候補も拒否する。
既存の基礎・敷地・中心座標は維持。明示した新しい保存版では、道路側の入口方位に合わせた任意角度の長方形外形を保存する。回転後に基礎からはみ出さないよう寸法を制限し、施設の必要面積も回転後の面積で判定する。表示と車両障害物は同じ向き・寸法を読む。基礎自体の作り直しや曲線輪郭は未実装。
設計時採光は朝8～夕16時の5点、200mまでの地形標本と建物屋根の保守的遮蔽。年積算や連続影の精密計算ではない。
この段階では現在の乾湿をリスクの代用とし、洪水再現期間は未実装。水車の流量・水利権、飲料水・鉱床等は未知のままなら配置しない。

## 受入の区別
保存・再生成の一致、条件外の拒否、原料リンク、道路接続、住居容量は機械検証する。
「歴史上必ずこの村になる」「自給できる」「現地測量済み」「実GPUで高速」はこれらの検証からは主張しない。
閾値はゲーム向け既定。文化・時代・気候別の調整と、生産量/労働力/サービス需要の数量接続は今後の段階。

日照操作の状態は現在ブラウザ内の世界別保存。持ち運ぶゲームセーブの時刻との統合は未実装。太陽の向き計算自体は独立した状態オブジェクトを受け取るため、呼出元の共通時計で駆動できる。

実例の既存3棟は今回の直線アクセス調査で乾いた通路を確認できず、向きを未変更で保持して警告する。迂回歩道の探索は未実装。これは旧村全体の通行可能性が合格したという意味ではない。
