# エンジン現状分析と課題整理レポート（Continuous Terrain Adapter）

> 履歴文書: 以下は0.3.4時点の問題分析です。現在は入口統一、海/湖の自動生成、
> Paged Globe、造成後の固定格子雨水、C1河床、道路横断形状などを実装しています。
> 現行の状態と未達条件は [HANDOFF.md](HANDOFF.md) と [PLANET_WORLD.md](PLANET_WORLD.md) の冒頭を参照してください。


更新日: 2026-10-09  
対象バージョン: `0.3.4`

---

## 1. エグゼクティブサマリー

`continuous-terrain-adapter` は、有限地域および全球の確定した数値場を任意のメートル座標で連続参照（C0/C1）するアダプターとして開発が進められてきました。現在、`npm test` は **246件すべてPASS** しており、Stage 0（設計）から Stage 5（Webビジュアライザ）までの骨格が一通り存在するように見えます。

しかし、急激な機能追加（特に複数ワーカーによる並行実装）の結果、以下の深刻な問題が蓄積しています：
1. **重複と乖離 (Drift)**: ルートディレクトリと `src/core/` でのコード二重管理、最新修正の未反映、および Core と UI で判定基準が異なる二重実装。
2. **極端な偏り (Bias)**: 河川幾何への過剰投資と湖沼・海洋・地下水モデルの軽視、D8流向の強い方向歪み、道路中心線のみに依存した横断勾配（排水性）の無視。
3. **根幹機能の未実装 (Missing Implementation)**: **造成（切盛土・建物）適用後に水系・排水が一切再計算されない完全な断絶**、全河床・法面境界におけるC1連続性の未完、マルチチャートでの水域跨ぎ不能。
4. **構想との決定的なギャップ**: **「Google Earth のような全球〜局地への連続ズームと階層的LODストリーミング」は現在まったく実装されておらず**、現状は単一の局所2D平面（最大100km）を Canvas 2D で表示するサンプリング計算機に留まっている。

## 2. 重複（Duplication / Redundancy / Drift）

### (1) ルート直下と `src/core/` の二重管理（16ファイルの完全重複と不揃いなShim）
- **16ファイルが完全重複（バイト単位で同一）**:
  `bernstein.mjs`, `channel-sizing.mjs`, `contract-validation.mjs`, `dynamic-drainage.mjs`, `dynamic-regional.mjs`, `field-math.mjs`, `hermite-field.mjs`, `json-contract.mjs`, `periodic-field.mjs`, `projected-canonical.mjs`, `projected-ground-bounds.mjs`, `road-crossings.mjs`, `spherical-detail.mjs`, `spherical-noise.mjs`, `spherical.mjs`, `surface-derivatives.mjs`, `surface-trace.mjs`, `surface-water.mjs`
  これらはルート直下と `src/core/` の両方に全く同じ実体ファイルが存在し、二重管理状態になっています。
- **10ファイルはShim化済み**:
  `building-pad.mjs`, `road-earthwork.mjs`, `road-junctions.mjs`, `global-terrain.mjs` などはルート側が `export * from './src/core/...'` の Shim になっていますが、上記の16ファイルは実体のまま放置されています。

  `test/*.test.mjs` や `scripts/*-worker.mjs` の多くが `../surface-water.mjs` のようにルート側のファイルをインポートしており、`src/core/` 側への移行が不完全です。

## 3. 偏り（Bias / Skew / Asymmetry）

### (1) 水系モデルの「河川偏重」と「湖沼・海洋・地下水の軽視」
- **河川への過剰投資**: Strahler次数による幅・深さスケーリング、放物線/台形断面、六次多項式極値、外岸smoothstepなど、1次元ラインから掘削する河道幾何には非常に多くの計算資源とコードが割かれています。
- **湖沼・海洋の単純化**: 湖（Lake）は単純な凸/凹多角形と単一の水平水位のみ。海（Ocean）に至っては独立したモデルが存在せず、単に地域グリッドの底に一律標高を与えているだけです。
- **地下水のモデリング不在**: 地下水（Groundwater）は単に `waterLevelRole: 'groundwater'` というフラグを渡し、地表下にあるときは水深を0として扱うだけの「ダミーフラグ」です。浸透流（ダルシー則）、帯水層（Aquifer）、地下水面（Water Table）、湧水などの物理モデルは皆無です。
- **湖・海の自動同定の永久延期**: 「利用者の指定により保留」として何度も先送りされ、自然な水系の同定・生成機能が片手落ちになっています。

### (2) 流向モデルの強い方向バイアス（D8 Flow Bias）
`dynamic-drainage.mjs` および `src/core/post-detail-drainage.mjs` で採用されている流向アルゴリズムは、45度刻みの古典的な **D8 (8方向)** に固定されています。
- 直交方向（1.0）と対角方向（$\sqrt{2} \approx 1.414$）で距離と勾配の歪みが発生し、グリッド軸に沿った不自然な直線状の流路（Grid Artifact）が形成されやすい偏りがあります。
- 斜面での発散流や扇状地を表現できる MFD (Multiple Flow Direction) や D-Infinity などの連続角流向モデルはサポートされていません。

### (3) 道路幾何の「中心線至上主義」と横断勾配（カント・クラウン）の無視
- 道路造成（`road-earthwork.mjs`）において、路面標高は中心線の高さを道路幅員（`halfWidthM`）方向へ**完全に水平（横断勾配ゼロ）**に延長しています。
- 現実の道路に必要な雨水排水用の**拝み勾配（クラウン: 1.5〜2%）**や、カーブでの遠心力対策である**片勾配（カント / Superelevation）**が全く考慮されていません。このため、道路面上は排水勾配が存在せず、水理学的に水が溜まる不合理な幾何になっています。
- 立体交差離隔（`inspectRoadGradeSeparations`）も**「中心線の交点（1点）」の鉛直差しか検査していません**。斜め交差した際に橋桁の角や橋台が下側道路の建築限界に衝突しても検知できません。

### (4) 投影法の単一性（正距方位図法 Azimuthal Equidistant のみの硬直性）
球面から平面への投影が `spherical-azimuthal-equidistant@1`（正距方位図法）の1種類しか用意されていません。正距方位図法は局所領域の中心付近では優れていますが、矩形領域の外周部や広域表示では面積や角度の歪みが急速に増大します。標準的な UTM、Webメルカトル、ランベルト正角円錐図法などが一切選べません。

### (5) テストデータと検証の過剰適合（Overfitting）
すべての統合テストおよび検証スクリプトが、`world-a`, `world-b`（地域）および `audit-a`, `audit-b`（全球）という**固定された4つの合成データ・固定シード**に依存しています。グリッドサイズも 48×24, 64×48, 96×72 という極めて粗いサイズばかりで、動的なサイズ変更、極端な高山・島嶼部、複雑なヘアピン道路など、多様な入力に対する堅牢性検証が偏っています。

## 4. 実装されていないといけないはずなのにされていないもの（Missing Implementations / Gaps）

### (1) 【最重要】造成（切盛土・建物）と水文（河川・排水）の完全な断絶
エンジン最大の設計上の断絶です。道路の切盛土（`road-earthwork.mjs`）や建物敷地の造成（`building-pad.mjs`）によって地表面標高（`groundElevationM`）が改変されますが、**造成後の地表面に対して水系（河川・流向・流域）を再計算・再統合するパイプラインが存在しません。**
1. **河川が盛土に埋もれる / 盛土に乗る**:
   道路盛土が既存の川を横断した場合、水面標高は造成前の自然地形のまま固定されるため、盛土によって川が地中に埋没するか、あるいは盛土の上に川が登る異常な水深計算になります（`building-pad.mjs` L243-244 に「Water levels stay fixed; runoff, flow and structural stability are not re-solved」と明記）。
2. **暗渠（Culvert）が地形サンプラーに組み込まれない**:
   `inspectEarthworkDrainage` は「ここに暗渠を通せます」という提案オブジェクトの配列を返すだけで、**`terrain.sampleAt(x, y)` には暗渠の管内水路も、盛土上流側の湛水（Ponding）も一切反映されません。**
3. **造成による流域・流向の変化の無視**:
   造成によって尾根や谷が切り崩されても、地形サンプラーが返す `basinId` や `outletCellIndex` は造成前の古い値のまま素通り（pass-through）します。

### (2) 「局所的C1」の看板倒れ（全河床・全岸・造成法面のC1連続性の未完）
「連続地形アダプタ（Continuous Terrain Adapter）」を謳い、ドキュメントでも C1（1階微分連続）をアピールしていますが、数学的な連続性は極めて限定的です。
- **C1なのは「何もない自然地形の基礎補間（HermiteField）」のみ**。
- 河道を掘削した領域の内部、中心線、屈曲点、合流部は区分線形や放物線による **C0折れ線（微分不連続）** です。
- 外岸のみ `smoothstep` で法線方向微分をゼロにして誤魔化していますが、自然地形が傾斜している場合、微分ゼロで接続すると自然地形の勾配との間に折れ曲がり（微分不連続）が発生します。
- 造成（切盛土）の法面端（batter toe）も同様に傾斜地盤との接続で勾配不連続が生じます。
- このため、`surfaceFrameAt` で法線や曲率（2階差分）を求めると、河道端や法面端で法線が急変し、擬似的な巨大曲率が発生または破綻します。

### (3) 全球マルチチャートにおける「面的な水域（Lake / Ocean）」のチャート跨ぎの不可能性
`connectInterChartRivers` により河川のチャート跨ぎは追加されましたが、**湖や海などの「面的な水域（Water Body）」はチャートを跨ぐことができません**。
- コード上で明示的に禁止されています：
  ```js
  if (node.bodyId) throw new RangeError('Inter-chart endpoint cannot be a water-body anchor');
  ```
- しかも複数チャートは矩形境界が互いに離れていなければならず（重複拒否）、**「チャートを跨ぐ広大な湖」や「全球を覆う海」をマルチチャートで分割表現する手段がありません**。

### (4) 車両・構造物の3次元幾何検証・建築限界の欠落
- **道路全幅での水没検査**: 中心線が水面上にあっても、幅員方向の路肩が水没しているケースを検知できない（コード内のコメントでも「not full road-width or structural acceptance」と認めている）。
- **斜め交差時の桁・橋台の建築限界干渉**: 平面交差角が浅い場合、下側道路の中心線から外れた位置で上側高架橋の桁下面と衝突するリスクを検査できない。
- **構造耐力・土質安定性**: 切盛土の法面勾配（0.5など）に対する土質力学的な安定計算（円弧すべり安全率）や、橋梁桁の許容スパン・荷重計算は一切未実装。

### (5) 詳細化後排水適応（`adaptPostDetailDrainage`）のスケール限界と強引な標高盛り上げ
- **セル数制限（`MAX_CELLS = 262144`）によるクラッシュ**: 少し高解像度な全球グリッド（例えば 512×256 で細分3＝1,179,648セル）で実行すると即座に `RangeError` でクラッシュし、実用規模にスケールしません。
- **標高の強制盛り上げ（Fill）のみで開削（Carving）がない**: 凹地を埋めるために地表標高を上方に強制改変（Fill）するだけで、実際の自然現象である「溢水による河床の開削（Breaching）」や水理計算は行われていません。
- **水系適用前の地形にしか使えない**: 河川や湖などの水系が載った後の地形には適用できず、水系と詳細化地形の整合性が取れません。

## 5. Google Earth的な連続＆LOD読み込み構想とのギャップ

### (1) 「LOD」という用語の決定的な意味のすれ違い
一般に Google Earth やゲームエンジンで言う **LOD（Level of Detail）** とは：
> *「視点（カメラ）の距離に応じて、遠くは粗い低解像度タイル、近くは高精細なメッシュやテクスチャへと動的に切り替えて読み込み・描画するストリーミング技術」*

しかし、本アダプタが実装し、テストしている「LOD」は全く異なる意味で使われています（`src/ui/lod-comparator.mjs` L1-5）：
> *「表示間隔（`spacingM` = 10m, 20m, 50m…）を変えて格子点をサンプリングしても、同じ $(x, y)$ 座標であればビット単位で完全に同一の標高・勾配・水深値が返ってくること（**サンプリングのLOD不変性・決定論的一致**）」*

つまり、**「動的に詳細を切り替えるストリーミング機構（Paged LOD）」を作ったのではなく、「粗くサンプリングしても細かくサンプリングしても値が狂わない数学的一貫性」を検証しただけ**という状態です。

### (2) 3D地球儀が存在せず「単一の局所2D平面（最大100km）」しか表示できない
1. **3D レンダラーが存在しない**: Webビジュアライザ（`src/ui/`）は HTML5 Canvas 2D による完全な2D平面マップです。Three.js、WebGL、WebGPU などの 3D グラフィックス基盤は一切導入されておらず、地球を球体として回転・俯瞰表示することすらできません。
2. **全球データから「最大100kmの局所平面」を1枚切り出しているだけ**: 全球地形であっても、画面にロードする際は `createProjectedTerrainView` により、「指定した緯度・経度を中心とした最大半径100km以内の正距方位図法の2D矩形」を静的に1枚切り出しています（`src/ui/scene.mjs` L46-51）。投影半径の上限が $0.1\,\text{rad}$（約100km）に厳格に制限されているため（`src/core/spherical.mjs` L31）、**「半球や地球全体を画面に収めるズームアウト」自体が例外（`RangeError`）で弾かれて不可能**です。
3. **場所の移動は「パン」ではなく「画面切り替え」**: 別の地域を見る場合、地球儀の上をシームレスに移動するのではなく、マルチチャートの切り替えボタン（‹ ›）を押して「別の局所チャートの2D平面に画面をリロードする」という仕様です。

### (3) タイル読み込み（`TerrainTile`）の限界
`src/ui/map-viewer.mjs` にある `TerrainTile` というタイルピラミッドクラスも、Google Earth 的なストリーミングとは程遠いものです：
- **メモリ上の単一シーンの描画負荷分散にすぎない**: 外部から非同期にタイルを取得する仕組みではなく、すでにメモリに丸ごとロードされている単一 Snapshot に対し、ブラウザがフリーズしないよう1フレーム11ms以内で少しずつ `sampleAt` を呼んで Canvas に描く負荷分散処理にすぎません。
- **データサイズの上限**: 全球データや詳細化グリッドは単一メモリ空間に収まるサイズ（262,144セル以内）に縛られており、地球全体の膨大なデータを階層的にキャッシュ・破棄しながら巡回する設計になっていません。

### (4) Google Earth 的な実装を実現するために必要な技術要素
1. **3D グラフィックス基盤の導入**: WebGL / WebGPU（Three.js, Cesium 等）による 3D 球面レンダラー。
2. **球面 QuadTree（四分木 / HEALPix / CDLOD）による Paged LOD**: カメラ距離と視錐台（Frustum）に基づいて動的にタイルをストリーミング生成・破棄するエンジン。
3. **大域 3D 地心直交座標系（ECEF）への移行**: 局所2D正距方位図法への静的切り出しを脱却し、全球を3Dベクトルで直接サンプリング・レンダリングするパイプライン。
4. **アウトオブコア（Out-of-core）データ管理**: タイル単位で遅延ロード・キャッシュ・解放できるチャンク型ファイルフォーマット。

## 0.4.0での進捗

本分析の「3D地球儀と外部入力ページのストリーミングが存在しない」という点は、0.4.0の `src/globe/` プロトタイプで対応した。球面ECEF・Cube-Sphere・WebGL 2、非同期Worker、入力ページとGPUの容量制限付きLRUを備え、同一シーン内で宇宙〜地表を移動できる。設計は [GLOBE_ARCHITECTURE.md](GLOBE_ARCHITECTURE.md)、数値・実画面・性能と未受入事項は [GLOBE_VALIDATION.md](GLOBE_VALIDATION.md)。上の分析は当時の状態を記録したもので、現在の実装状況はこれらの文書とROADMAP末尾を参照する。水理・全河床C1・全幅離隔・大規模保存契約などの残課題まで解消したとは扱わない。
