# 全球から地表までの Paged Globe アーキテクチャ（0.4.0）

> この文書の数値・保留事項は上流0.4.0時点の履歴です。現在の自動水域・集落・LOD・保存の実装と最新検証は [PLANET_WORLD.md](PLANET_WORLD.md) / [ROADMAP.md](ROADMAP.md) を参照してください。旧GPU測定を現在のクラウド実装の性能証明として使いません。

## 目的と現在の納品範囲

`src/globe/index.html` は、一つの球面・一つのWebGLコンテキスト・一つのカメラで、20,000kmの宇宙視点から数mの視点まで移動するプロトタイプである。ホイール、連続高さスライダー、パン、視点の傾き、連続ツアーを備える。ズームに伴うページ遷移、Canvas 2Dへの切替、地域シーンの再読込はない。旧2Dビューアから `3D Globe` で開ける。

合格した数値試験と、実ブラウザの動作測定は別の証拠として扱う。fps・メモリの実測値と受入の未達事項は [GLOBE_VALIDATION.md](GLOBE_VALIDATION.md) に記す。水域自動化の保留を維持し、青い水面は明示モデルの湿潤範囲だけを表示する。

## 選定

| 項目 | 採用 | 比較と理由 |
|---|---|---|
| 大域座標 | Coreと同じ球面のECEF。CPUは倍精度、GPUはタイル局所＋カメラ相対座標 | 緯度経度平面の巨大座標と極・日付変更線の切替を避ける。WGS84楕円体に変更するとCoreとの位置契約が変わるため、この段階では採用しない |
| 階層 | 6面Cube-Sphere四分木、L0〜L24、各タイル16×16セル | 極に特異点を持つ緯度経度タイルに比べ、全球を同じ階層で扱える。HEALPixの面積均一性よりも、矩形メッシュ・親子対応の単純さを優先。CDLODは近距離用途に適するが、今回は球面四分木を共通の入口にする |
| 描画 | 外部依存のないWebGL 2 | Workerが生成した頂点を転送でき、既存の軽量配布を維持できる。Three.js/Cesiumによるカメラ・タイル管理の導入は既存Coreとの評価経路を別途接続する必要がある。WebGPUは対応端末とGPU計算精度の検証を後続とする |
| 詳細化 | 基礎地形の勾配上限＋球面曲率＋丸めによる幾何誤差の画素投影、格子間隔、可視・地平線判定、最大要求数 | 基礎地形は2画素を目標にする。予算内で誤差の大きい候補を先に分割し、未達・不明・予算制約を記録する。地物の誤差認証は後続 |
| 非同期 | 2本のmodule Worker、優先要求、AbortController、Transferable | サンプリング・境界切り出し・メッシュ生成をメインスレッドから移す。固定本数にしてメモリとCPU負荷を限定する |
| キャッシュ | 入力ページとアンカー値、フィーチャー、GPUバッファに別の容量制限付きLRU | 数値場全体をWorkerへ複製しない。親・表示中の階層を保護し、表示から離れたタイルを容量不足時に解放する |
| 継ぎ目 | 共通Cube辺座標、外周スカート、階層順の双方向モーフ | 子4枚が揃うまで親を維持。親が細形状になってから孫の細分化を開始し、縮小時は孫の復帰を終えてから親へ戻す。遷移中の兄弟4枚をLRUから保護する。隣接LODのステッチは後続 |

SSEに基づく階層選択と親子の描画準備は [Cesium Nativeの選択アルゴリズム](https://cesium.com/learn/cesium-native/ref-doc/selection-algorithm-details.html)、地形のスカートと誤差調整は [Cesium GlobeのAPI](https://cesium.com/learn/cesiumjs/ref-doc/Globe.html) を比較資料にした。実装コードは独立した小規模プロトタイプである。WebGL 2の描画仕様は [Khronosのリファレンス](https://www.khronos.org/files/webgl20-reference-guide.pdf)、GPUタイマーは [EXT_disjoint_timer_query_webgl2](https://registry.khronos.org/webgl/extensions/EXT_disjoint_timer_query_webgl2/) に従う。

## 数値場もページ化する

実行時に完全なsnapshotを読み込んでからメッシュだけを小分けする構成にはしていない。

1. `scripts/package-globe.mjs` が、検証済みCore snapshotをオフラインで16×16セルのFloat64LEファイルへ分割する。
2. `manifest.json` は座標・seed・詳細化帯・極の平均・緯度帯ごとの解析的勾配上限・ページのパス/サイズ/SHA-256を持つ。標高配列を持たない。
3. Workerは照会点の最大4×4の近傍セルに必要なページをfetchする。未読なら照会を待機し、読込後に同じ演算を再開する。
4. 全球のHermite補間、極のキャップ、詳細化、SHA-256はCoreの共有実装を使う。参照配列が常駐かページ内かで計算式を変えない。読んだCoreセルの高さ包絡からタイルの保守的高さ範囲も求め、全球の最大起伏を局所タイルすべてに当てはめない。極キャップには平均とリング範囲を使う。
5. `anchored-spherical-residual-bands@2` のアンカーも必要位置で生成し、全アンカー配列を作らない。極の集計値は事前に保存する。旧 `bounded-spherical-bands@1` も対応する。
6. 明示水系チャートは視域が近づいたときに個別のレシピを読む。デモは河川・橋・道路造成・建物敷地、実生成例は2世界・8チャートを含む。

入力ページとフィーチャーレシピのサイズ・SHAが合わない場合はエラーにし、別の地形として黙って描画しない。`reference.snapshot.json` はNode照合用の保存物であり、ブラウザがfetchするファイルではない。

格子間隔の目標は通常28画素、カメラ高度5000m未満で明示フィーチャーの範囲と交差するタイルは8画素にする。水際・細い道路・敷地の輪郭が地盤の粗い三角形に隠れないよう、地物の視認範囲を優先する。分割候補の優先度にもこの目標を使い、512要求の予算を共有する。これは厳密な幾何誤差証明の代わりになるものではない。

### 基礎地形の誤差判定（2026-10-10）

`lod.mjs` は保存済みの緯度帯・極キャップの勾配上限をタイル全域について集計する。Cubeの正規化写像は面内で二階微分ノルムが6以下であるため、セル三角形のパラメータ直径を `d = 2√2 / (16 × 2^L)`、基礎標高の絶対上限をH、勾配上限をK、球半径をRとして、基礎三角形と連続Core曲面の距離を `K R d + 3(R + H)d² + 丸め上限` で抑える。頂点のみの標本から内部の誤差を推測する方式ではない。メッシュには実際のFloat32丸めと親形状までの最大変位も記録する。

投影はタイル包絡球の最小奥行きと最大横距離から透視投影の微分上限を求める。近クリップ面を跨ぐ場合や勾配メタデータが欠ける場合は不明として細分化を要求する。物理フレームバッファの高さを使い、DPRも反映する。512要求・1600ノード・L24の制約に達した場合は2画素を保証せず、`lodQuality` に計画葉の未達数・不明数・最大値・予算制約を出す。

この認証の対象は**モーフしていない基礎全球地形の三角形**。水系掘削・道路・敷地の高さ変位は別の振幅上限（2倍の垂直余裕）として記録し、地物の勾配・輪郭・水際の収束誤差とは扱わない。基礎LODには地物の高さ余裕を混ぜず、可視判定には含める。親を描いている生成待ちやモーフ中の実画面誤差と、計画葉の誤差も別である。隣接タイル間の2:1制約・辺ステッチ・局所細分と水際の厳密な誤差上限は未実装。

## Coreとの一致

`src/core/hermite-kernel.mjs` と `global-field-evaluator.mjs` を常駐/ページ両経路で共有する。演算の順序を保持し、旧worldIdと保存済み数値を維持する。標高の細部を表示LODで再生成・省略することはない。

明示水系は保存済みのフィット幅とCoreの `compileSurfaceWater`、道路は `createRoadAdjustedTerrain`、敷地は `createBuildingPadAdjustedTerrain` を使う。Cube上の頂点を球面点へ戻してこれらを照会する。橋の地盤とデッキを別に描く。冠水域と道路端はCore判定で三角形を切り出し、局所LODでは固定メートル差分からCore法線を計算する。水面は3mm、舗装は20mmだけ描画上の深度競合を避けるため浮かせる。照会・証拠値はこのオフセットを含まない。

同じNode実行環境内では、常駐配列とページ経路の基礎全球標高をIEEE-754の完全一致で試験する。NodeとChromiumの間には三角関数等の丸め差があるため、実ブラウザの標高・水深は1e-9m以内、法線は1e-9以内、カテゴリとIDは一致を要求する。既存水系チャートとの照合は、投影の往復丸めを含め標高・水深1e-7m以内、水位・水源IDは一致を要求する。描画用のpack IDと元の `canonicalWorldId` を別に保存する。道路・敷地を加えたデモは、元の水系snapshotそのものと同一worldIdだとは扱わない。

細い道路を粗い地形三角形の色に広げないよう、道路・水面・敷地は独立したCore判定の面にする。L16以上では地物の外接範囲に交差する地盤三角形も最大6回細分化し、最長辺1.5mを目標にCore標高と法線を再照会する。粗い地盤が正しい水面や舗装面を隠す現象を抑える。元の三角形の辺上では細分辺と元の辺の平面を表示用の壁でつなぎ、T字接続による穴を覆う。1タイル4096枚の地物三角形を上限とし、予算を超える場合は地盤を粗いまま保持する。全域の水際誤差上限、局所境界の壁の見え方、非常に細い地物の取りこぼしは未受入である。

GPUの頂点は、各タイル中央の実標高を含む倍精度ECEFを原点にしてからFloat32へ変換する。フレームごとにCPUでタイル原点−カメラ位置を倍精度で引き算する。大域座標をそのままFloat32で引く方式は使わない。深度は対数深度を用いて宇宙〜地表の比率を扱う。

メッシュ内部は三角形による表示近似であり、任意点のCore値と同一の連続曲面そのものではない。インスペクター値は表示頂点の補間値ではなくCore照会値である。現在のLOD条件はすべての地形・水際について厳密な画面誤差上限を証明するものではなく、これを次の品質課題とする。

## 有限リソースと復帰

| 管理対象 | 上限/方針 |
|---|---|
| Worker | 2本、各1ジョブ。範囲外要求はキャンセル |
| 標高ページ | Workerごと256KiBの実バッファ容量 |
| 手続きアンカー | Workerごと128KiBの計算上の項目予算。JSオブジェクトの実heapは別 |
| フィーチャー | Workerごと8MiBの推定項目予算。モデルの実heap測定は別 |
| GPU頂点/索引 | 既定64MiB、明示選択時128MiB（うち村用1MiB）。確保前にLRUから削除して予算を予約。地物周辺の地盤細分と親を保持する容量を確保 |
| 要求メタデータ | 最大512タイル、階層の走査最大1600ノード |
| メイン側転送待ち | 生成中の予約を含め4枚。フレームあたりupload 1枚 |
| 証拠保持 | 頂点標本128件、フレーム標本30,000件まで |

親を保持して子を準備する。初めて必要になる領域では粗い親が表示される。既に取得した根6枚は小さいフォールバックとして保持する。予算が足りなければ親を残し、詳細化のために無制限に確保しない。タイル削除時にはVBO、IBO、VAOをdeleteし、ページ終了時にはWorkerと全キャッシュ・GPUプログラムを破棄する。GPUコンテキスト喪失時は状態を知らせる。

上記の管理バッファ量はブラウザ全体のメモリ測定値ではない。JS Map・DOM・Worker heap・ドライバ・ブラウザプロセスの追加使用量がある。512MiB〜1GiBのプロセス上限をこの表だけで受入済みにはしない。

## 起動と既存データの変換

パッケージディレクトリで `npm run ui` を実行し、`http://127.0.0.1:3000/src/globe/index.html` を開く。デモpackは同梱済み。`npm run globe:package` で再生成できる。

```powershell
node scripts/package-globe.mjs --snapshot examples/audit-0.3.3/0.3.5/audit-a.snapshot.json --out examples/globe/0.4.0/real-a
```

生成したpackはURLの `world` で指定する：

`/src/globe/index.html?world=../../examples/globe/0.4.0/real-a/manifest.json`

基礎全球@1、明示水系@1/@2を変換できる。Coreの既存上限131,072セルは維持する。固定細分排水補正snapshot、旧有限地域世界の全球埋込み、ユーザーによるブラウザ内の任意snapshot変換は本版に含めない。

## 固定メモリプリセット（2026-10-10）

画面の「地形メモリ上限」で64/128MiBを明示選択する。URLの `meshBudgetMiB` に保存し、
雨水/車両/橋の画面から戻っても維持する。未指定は64MiB。任意値や無制限値は拒否。
容量不足で勝手に128MiBへ上げることはない。世界ID、生成条件、Coreの値は変化しない。
各上限の80%を目標計画、20%を表示遷移に予約。高設定も有限LRUで管理し、
要求/訪問ノード数は最大6144/19200、Worker数は2のまま。
これは管理する形状バッファ量であり、JSヒープ/描画ドライバ/ブラウザ全体の上限とは別。
表示2画素が予算内で達成できたかは、表示中の誤差とプロセスメモリの実測で別途判定する。

## 2026-10-10: 橋端の垂直地盤面と誤差の区別

橋の下を埋めないため、地盤の高さ関数は盛土と橋下の境界で不連続になり得る。
その境界を一枚の傾斜三角形で渡すと、実際には存在しない斜面が水路側に張り出す。
`ground-breaklines.mjs` は保存済みの直線道路の区間種別から境界を得る。
境界の両側を正本で別々にサンプリングし、上面・下面・垂直面に分ける。
湾曲/折返し道路と複数境界の一般形は未対応で、既存の保守的な表示へ戻る。
世界の標高・保存ID・橋脚構造は変更しない。

### 同じ場所の高さ誤差と、表面までの距離は別

垂直面を含む地形には、一つの水平位置に複数の表面高度がある。
旧 `cellGroundErrorM`（半径方向の補間差）は引き続き記録する。
これと別に、実際に描画した壁の辺を使った空間距離上限を記録する。
段差の高さを恣意的に差し引いたり、試験標本の最大値を証明上限に使ったりはしない。

- 正本→描画：球面セルの角度範囲と正本の標高区間から、セル中心方向の軸成分と横成分を囲む。
  実際の壁の辺上で軸成分が最も近い点を選ぶ。軸方向の不足量と横方向距離上限の二乗和から距離上限が得られる。
  辺は同じタイルの実際の描画三角形に含まれるものだけを使う。
- 描画→正本：正本の地盤は、区分的連続な高さ関数に垂直段差面を含めた「地盤の立体境界」として扱う。
  正本標本の間を結ぶ細分三角形の軸成分は、標本間の閉じた地盤面でも取られる。
  両点が同じ球面セルにあるため、距離はセルの横方向直径 `2 (R+h_max) sin(angle)` 以下。
- 両方向の大きい方を使う。従来の区間上限も残し、利用可能な厳密な上限の小さい方を選ぶ。
  Float32丸めを加算し、親モーフ/辺ステッチは従来どおり別途加算する。

この証明は地盤表面の位置についてであり、法線、遮蔽、水際、道路/建物オーバーレイ、表示スカートを認証しない。
特に「半径方向の標高誤差が縮んだ」「村全体が受入済み」とは言わない。
実6タイルの384点照合と、純粋な幾何上限の回帰試験を保存した。

### 実タイル外の段差を混ぜない区間

タイルを囲む円盤だけでは、四角形の外にある橋端まで含み、段差がないタイルも3m以上の誤差を持ってしまう。
球面四角形を `normalize(sum(weights * corner))` と表し、チャート基底との内積 e,n,u から
投影座標 `R atan2(hypot(e,n),u) / hypot(e,n) * (e,n)` の範囲を計算する。
正規化係数は打ち消される。共通の倍率を包絡し、道路の方向ごとに e,n の相関を保つ。
投影位置が区間の外側にあり、隣の区間の内部方向へ射影されることが保証されれば、
共有端点しか選べない候補は必ず遠いため除外する。曲がった道路でも、この優越条件が証明できる場合に限る。
円盤入力だけの既存呼出しは従来と同じ。新しい制限は描画セルの実四隅を持つ場合だけ使用する。

### 一様な水域の近景（2026-10-10）

水底の区間をそのまま水面の可視性に使うと、斜視で水面が消える。
表示判定は水面/橋面も包含し、地盤の精度証明と混同しない。
さらに、一様な貯水面が領域全体を覆う場合だけ、隠れた水底ではなく水面をLODの対象にできる。

- 球面タイルを包含する球面キャップから緯度/経度の区間を作る。
  極を含むもの、大きすぎるもの（64補間パッチ超）は不明として通常経路へ戻す。
- その区間と交わる全補間パッチの4頂点を調べ、全てが同じ貯水面を選ぶことを要求。
  旧halo方式、複数湖の競合、局地地物、より高い河川水面は最適化しない。
- タイルの地盤上限と親地盤の上限が、水面の三角形の弦の沈み込み/丸め誤差を含めても水面より下にあり、カメラが水面より上の場合だけ適用する。
- 水面は地盤モーフによって移動しない。16×16セルの各三角形の球面弦誤差、3mmの表示オフセット、Float32丸めを計上する。
  画面への投影ではその誤差を含む高さ区間を使う。
- この条件の水底を可視地盤の件数から除き、`submergedGroundTiles` と水面誤差を別に出す。
  水面の誤差が未達/不明ならUIは目標達成と言わない。

これは一様な水面内部のLOD規則。一般の水際、異なる水域の境界、異LOD間の水面の継ぎ目、透明な水や水中カメラの完成を意味しない。
世界の正本、海/湖の水位、サンプル、地形メッシュ生成そのものは変更しない。
